# Build trustworthy autonomy across software lifecycles

**Our factory incorporates useful request-to-PR practices, but it does not yet provide full SDLC coverage, independent self-monitoring, or automatic infrastructure recovery.** Its live code prepares an existing repository, supplies pinned skills, investigates before planning, pauses for answers and approval, implements in one coding session, repairs some review/test failures, verifies a commit and attempts real PR publication. These are implemented paths, not proof of successful live operation: T3 is installed and reachable, but a credentialed end-to-end coding/GitHub run remains unqualified. Greenfield bootstrapping and modernization programs need explicit workflows. Deployment and production recovery remain outside the current PR boundary. This assessment draws on targeted primary-source research and repository inspection; it is neither exhaustive research nor an enterprise compliance assessment.

## Repository editing covers only part of delivery

DORA describes continuous delivery as keeping software safely releasable, supported by testing, integration, deployment automation, version control and security. A PR-producing agent addresses part of that system. Our recommended lifecycle is requirements and acceptance criteria, context and baseline, design and risk, implementation, verification, artifact/PR, controlled release, deployment validation, operational feedback and maintenance. Release automation also needs versioned packages, configuration, environment preparation and smoke tests. ([DORA continuous delivery](https://dora.dev/capabilities/continuous-delivery/), [deployment automation](https://dora.dev/capabilities/deployment-automation/))

**Keep one coding session per request and introduce workflow profiles.** Greenfield should establish product constraints, architecture decisions, approved scaffolding, dependencies, repository/CI bootstrap and initial deployment/observability configuration. Brownfield should establish relevant behavior, dependency and contract impact, baseline failures and focused acceptance evidence before planning. In poorly tested legacy systems, begin with high-value acceptance checks around changed functionality rather than requiring comprehensive retrospective coverage. ([DORA test automation](https://dora.dev/capabilities/test-automation/))

Modernization needs additional program state: business outcomes, behavior to preserve or intentionally change, estate/dependency inventory, target architecture, migration increments, compatibility checks, coexistence, data transition, cutover and retirement criteria. Strangler Fig and Branch by Abstraction provide ways to replace behavior incrementally while maintaining a working system. Source inspection alone cannot establish which behaviors are actually used; runtime and business evidence matter. ([Strangler Fig](https://martinfowler.com/bliki/StranglerFigApplication.html), [Branch by Abstraction](https://martinfowler.com/bliki/BranchByAbstraction.html), [modernization with GenAI](https://martinfowler.com/articles/legacy-modernization-gen-ai.html))

The current [live state machine](/Users/Harshini.Battula/software-factory-core/packages/pipeline/src/factory_pipeline/autonomous.py) requires an existing branch and real files, and its discovery contract contains findings, file names and questions. It does not require baseline test receipts, a dependency map or acceptance-evidence traceability. Its [skill mapping](/Users/Harshini.Battula/software-factory-core/packages/pipeline/src/factory_pipeline/skills.py) supplies debugging guidance to every discovery task rather than choosing discovery instructions by project type. Those are concrete expansion points.

## Bounded code repair is not independent self-healing

The code has persistent stage state, pending-operation intents, branch/SHA checks, bounded review/test repairs, deadlines, kill-switch polling and attempted T3 interruption. These help supervise work. **There is no independent stale-run watchdog, automatic side-effect reconciliation, active telemetry pipeline or actionable alerting in the live path.** Generic “session running” polling indicates liveness, not meaningful progress. Temporal itself recommends idempotent activities and heartbeat checkpoints because external work can finish before a worker crashes without reporting completion; durable orchestration does not make arbitrary external effects exactly once. ([Temporal activities](https://docs.temporal.io/activities), [activity definition](https://docs.temporal.io/activity-definition))

Two P0 defects emerged. [FactoryRequestWorkflow](/Users/Harshini.Battula/software-factory-core/apps/worker/src/factory_worker/workflows.py) reports `completed` through its query/return even after the pipeline finishes failed or killed, although database status preserves the failure. Also, three-day human waits conflict with the live one-hour deadline, which includes waiting; an approved request can immediately expire. Fix terminal-status consistency and separate active-execution budgets from human-wait deadlines before relying on monitoring.

Next, record meaningful progress timestamps, add actual activity heartbeats, classify retryable infrastructure faults separately from permanent failures, and reconcile uncertain launches/publications using leases and fencing. Monitor queue age, stage duration, failure rates, worker/session health, saturation and verification/publication outcomes. Export correlated traces, metrics and logs rather than treating database events or a stdout exporter as complete observability. ([Google SRE monitoring](https://sre.google/sre-book/monitoring-distributed-systems/), [OpenTelemetry signals](https://opentelemetry.io/docs/concepts/signals/), [Collector](https://opentelemetry.io/docs/collector/))

Factory recovery, code repair and product production recovery are separate capabilities. Production healing requires deployment identification, health evaluation, incident deduplication and preauthorized mitigation. Canary rollback can limit exposure, but reverting a binary does not necessarily repair transformed or corrupted data. Production changes require separate scoped authority; a generic coding session should not gain unrestricted access. ([Google SRE canarying](https://sre.google/workbook/canarying-releases/), [on-call guidance](https://sre.google/workbook/on-call/))

## Enterprise controls must survive ignored instructions

Skills guide work; **permissions, isolation, identity, quotas and publication boundaries require executable enforcement**. A worktree does not isolate host resources or credentials. The current runtime explicitly documents trusted single-host execution, self-review, missing hard dollar enforcement and manual reconciliation. Agentic threats include instruction hijacking, tool misuse and inherited privilege abuse. Scope credentials to a run and repository, isolate workers from the control plane, namespace tenant state and enforce authorization server-side. ([OWASP goal hijack](https://genai.owasp.org/agentic-applications-2026/asi01-agent-goal-hijack/), [identity and privilege](https://genai.owasp.org/agentic-applications-2026/asi03-identity-and-privilege-abuse/))

Preserve traceability from request and risk decisions through tested SHA, runtime/model/skill versions, command outcomes, artifact and release. NIST SSDF addresses preparation, protection, secure production and vulnerability response across the lifecycle. SLSA separately addresses build provenance and isolation: content hashes alone are not signed provenance or evidence of a SLSA level. ([NIST SSDF](https://csrc.nist.gov/projects/ssdf), [SLSA build requirements](https://slsa.dev/spec/v1.2/build-requirements))

## Expand only after measurable qualification gates

First, fix the two P0 defects and qualify brownfield execution in a dedicated repository. The gate should require correct branch/SHA handling, real tests and PR, truthful terminal status, rejection and timeout behavior, and confirmed interruption. Crash immediately around launch, send, push and PR creation; require no duplicate sessions or PRs and no publication of an unverified commit.

Second, add isolation, authorization, quotas, watchdog/reconciliation and actionable telemetry. Prove cross-tenant denial, retry limits, safe recovery and alert delivery with fault injection. Third, introduce greenfield and modernization profiles with held-out representative tasks: bootstrap a buildable application; repair a real regression; migrate a component while preserving defined behavior and data contracts. Measure repeated-task completion, false success, regressions, human intervention, latency and actual cost where available. Regression tests of Python contracts do not establish model+harness task success. ([Agent evaluation guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents))

Finally, extend PR work through CI/review monitoring, artifacts, environment promotion, deployment verification and operational feedback. Establish a declared language/framework/platform support matrix. Broad SDLC support becomes credible through qualified scenarios and enforced boundaries, not one universal prompt. The monitoring/recovery controller can remain ordinary software around a single coding session; this direction does not require multi-agent coding orchestration.
